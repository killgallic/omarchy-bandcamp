# Omarchy Bandcamp v1.0.0 Implementation Plan

> **For agentic workers:** Execute these tasks inline with tests before implementation and review at each checkpoint.

**Goal:** Make a clean, installable, contributor-ready v1.0.0 release candidate that passes Omarchy validation and can be published from the empty upstream repository.

**Architecture:** Keep the tracked plugin directory source-only. Install the locked Python runtime under `$XDG_DATA_HOME/omarchy-bandcamp/venv`; the backend launcher uses that runtime while developer tests may use a local `.venv`. Publish the Git checkout as the plugin, with a tagged source archive as a convenience artifact. Keep account data in the existing XDG config/state/cache locations and credentials in Secret Service.

**Tech stack:** Omarchy 4/Quickshell, QML, Python 3.11+, uv, mpv, GitHub Actions.

---

### Task 1: Runtime outside plugin checkout

**Files:** `bin/setup`, `bin/backend`, `tests/run-python`, `tests/test_setup.py`, `README.md`.

- [ ] Write an isolated installer test using a temporary HOME/XDG_DATA_HOME and stub `uv`, `mpv`, and `secret-tool`; assert `UV_PROJECT_ENVIRONMENT` points outside the source directory, no `.venv` appears there, and desktop launcher/icon install under the selected XDG directory.
- [ ] Run `tests/run-python` and confirm the new test fails because setup currently selects the project `.venv`.
- [ ] Change setup to run `UV_PROJECT_ENVIRONMENT="$data_dir/omarchy-bandcamp/venv" uv sync --frozen`; change backend to execute that interpreter, retaining `.venv` only as a developer fallback; let `tests/run-python` find either environment.
- [ ] Run the installer test and full Python/QML suites. Commit the runtime change.

### Task 2: Validate the distributed plugin

**Files:** `tests/check-package`, `.github/workflows/ci.yml`, `.github/workflows/release.yml`.

- [ ] Make package checks compare `manifest.json` and `pyproject.toml` versions, require a clean tracked source tree with no symlink entries, and validate the desktop entry when `desktop-file-validate` exists.
- [ ] In CI, stage `git archive HEAD` into a temporary directory and run `omarchy plugin validate` where Omarchy is available; on this machine run it manually against the clean staged archive and record the result.
- [ ] Make the release workflow consume maintained v1 notes and verify the tagged archive before it creates a draft release. Keep release publishing tied to a reviewed `v1.0.0` tag.
- [ ] Run package, Python, QML, shell syntax, and desktop-entry checks. Commit release gates.

### Task 3: Contributor and user-facing release material

**Files:** `README.md`, `CONTRIBUTING.md`, `SECURITY.md`, `CHANGELOG.md`, `docs/releases/v1.0.0.md`, `docs/UPSTREAM_SUBMISSION.md`, `manifest.json`, `pyproject.toml`.

- [ ] Rewrite quick start for a public clone: `omarchy plugin add <URL> --enable`, run `bin/setup`, search Bandcamp from Super+Space; explain update, removal, data retention, troubleshooting, and Bandcamp Subsonic limitations without machine-specific claims.
- [ ] Document local development, tests, style, privacy rules, PR expectations, and issue reproduction with no account secrets; give a security contact route without publishing credentials.
- [ ] Set both project and manifest versions to `1.0.0`; write a concise feature/limitations changelog and release body.
- [ ] Run checks and inspect `git diff --check`; commit docs and version.

### Task 4: Fresh install and live upgrade rehearsal

**Files:** no new product files unless a concrete failure is found.

- [ ] Build a source archive from the release candidate, extract it into a temporary directory, and run `omarchy plugin validate` there; verify no symlinks or runtime files are packaged.
- [ ] Run `bin/setup` from a clean staged tree with temporary HOME/XDG dirs, then execute `bin/backend` under an isolated D-Bus session and confirm it starts with no account credentials.
- [ ] Fast-forward the live local checkout after checks, run setup to create the external runtime, restart Omarchy shell and Bandcamp, and verify the launcher, bar lifecycle, login restore, and collection load.
- [ ] Record the release candidate SHA and exact test results in `docs/releases/v1.0.0.md` only if the outcomes are reproducible.

### Publication checkpoint

The public GitHub repository currently has no default branch. Prepare a local `main` pointer and the exact `v1.0.0` tag/release commands after the candidate passes. Ask for final publication approval only once the candidate and release notes are reviewable. On approval, push `main`, create/push the reviewed tag, wait for CI, and confirm the draft release before making it public. Marketplace submission follows separately.
